# PREREG — Span-01 as a vasana firing sensor (2026-09-27)

**FROZEN** at this commit: `battery.json`, `questions.json` and `excluded.json`
are final, and any edit after this voids the run.

Written and committed before any Span-01 call returned data. Today's attempt
was blocked by the workspace's zero-data-retention guardrail, so no data exists.

## Question

Can `respan/span-01`, a behavior-scoring model on OpenRouter's Decisions API
(`POST https://openrouter.ai/api/alpha/decisions`), tell three vasana-relevant
behaviors apart from look-alikes well enough to justify prototyping a
hook-driven sensor for vasana-system?

Why this is the question: vasana-system's recorded weak point is *firing*.
The SessionStart hook asks the working model to notice patterns, and the
research-toolkit firing-filter README records that corrections were always
forced from outside. Keyword matching can't tell a principle being used from
one being mentioned. A separate scoring model is the untested middle option.

## What is gated

Only the decision to **build a prototype hook**, which is unshipped and
uncommitted to any plugin. Nothing reaches consumers on this evidence alone;
a shipped hook would need its own prereg on real transcripts.

## Arms and inputs

- One arm: `respan/span-01`. (Span-01 Lite is not tested here.)
- Stimuli: `battery.json`, generated by `gen.py`, with 88 synthetic items and no
  personal data. Per behavior (positives / plain negatives / hard negatives):
  B1 interaction-reframe 14/5/10, B2 principle named then violated 16/5/10,
  B3 stuck loop 13/5/10. Frozen at the commit that marks this file FROZEN.
- Question wording is `questions.json`, emitted by `gen.py`. The same pinned
  definitions set the labels and are what Span-01 is asked.
- One request per span, carrying all three questions. Only `state` is sent
  (never id, kind or label), in shuffled order. The runner script lives
  outside the repo; its whole contract is stated in this paragraph.
- The primary analysis uses each span's own-behavior answer. The other two
  answers per span are reported as **exploratory cross-scores**, carry no
  ship weight, and are not labeled in advance.

## Label validation (before scoring)

A Fable agent labels a shuffled copy blind, with no access to the author's
labels. **Any span where the blind label disagrees with the author's label,
or is "unsure", is excluded from scoring**, and the exclusions are listed in
the results. If a behavior loses more than 30% of its spans this way, that
behavior is VOID (the definition is too ambiguous to test), not failed.

## Endpoints (computed from the raw API responses, not from any summary)

Per behavior, with p = the returned probability that the behavior is present:
1. AUROC over all retained spans.
2. Precision and recall at a threshold of p >= 0.5.
3. Hard-negative gap: mean p(positives) minus mean p(hard negatives).

## Ship rule (prototype yes/no)

A behavior **passes** iff AUROC >= 0.85 AND precision >= 0.80 AND recall
>= 0.60 AND the hard-negative gap is >= 0.30.

**Build the prototype iff B2 passes AND at least 2 of 3 behaviors pass.**
B2 is mandatory because telling use from mention is the one thing keyword
matching provably can't do. If Span-01 can't do it either, it adds nothing
over the existing lexicon layer.

## VOID conditions

- More than 10% of requests error or return no probability → the whole run
  is VOID and gets re-run once, unchanged.
- The battery is edited after the first scored call → VOID.

## Known limits (stated now so a pass isn't oversold)

- n = 20 per behavior means wide intervals. A pass means "worth prototyping",
  not "works".
- The spans are synthetic and short. Real sessions are long and messy, and
  that gap is untested here.
- The spans are author-written. The blind relabel checks the labels, not
  whether the spans are representative.
- Respan retains request data, which is why the ZDR guardrail excluded it.
  So this run uses synthetic spans only; a real-transcript run needs a
  separate privacy decision.

## Residual confound (known, not fixed)

B2 plain negatives are still shorter than most B2 positives (at most 160
characters against up to 688). This is why the hard-negative gap, not the
plain set, carries the gate.

## Revision history (all before any data)

- v1 (60 items) was critiqued by a Fable agent. Verified finding: length and
  turn shape alone separated every positive from every plain negative. For
  example, B1 positives ran 264-341 characters and every B1 negative was 156
  or less.
- v1 got 60/60 agreement from the blind relabel. The critique shows why: the
  items were too easy, so a clean relabel was not evidence of a sound test.
- v2 adopts the critique: pinned definitions; same-shape plain negatives;
  same-frame, no-revision and reframe-without-pushback hard negatives (B1);
  violation-without-principle, argued exception, verbatim quote, cross-turn
  and user-violates items (B2); evidence-ignoring, varied-wording,
  rationalised and interrupted loops, plus warranted-retry and
  unapplied-instruction hard negatives (B3). The v2 blind relabel runs
  against the pinned definitions and the exclusion rule above applies to it.

## v2 blind relabel result (before any data)

A fresh Fable agent, shown only the pinned definitions and the shuffled spans,
had 0 disagreements and 2 "unsure" out of 88. Both are excluded per the rule
above and listed in `excluded.json`:
- B2-06: it is unclear whether "I'll keep this short" is a principle.
- B3-10: it is unclear whether an unevidenced mechanism counts as "engaging
  the failure".

Exclusion rate: B1 0/29, B2 1/31, B3 1/28. All are under 30%, so no behavior
is VOID.

## Deviations after launch

(Any change after launch is recorded here with its reason, before scoring.)

- **2026-09-27, request encoding (runner only; recorded before any scored data).**
  The first launch returned HTTP 400 on all 88 requests, so no probability
  came back and nothing was scored. The API rejected the `state` shape. The
  battery stores each span as a list of `{role, content}` messages, but
  Respan accepts `state` only as a string, or as an object
  `{input: [messages], output: <assistant message>}`. Five spans end on a
  user turn (B1-14, B1-16, B1-26, B3-14, B3-15, all negatives), so they
  cannot take the object form. Mixing forms would tie the input format to
  the label, a cue the model could score on. Fix: the runner serialises
  **every** span the same way, as a string transcript: each message becomes
  `User: <content>` or `Assistant: <content>`, with messages joined by a
  blank line. Content, order and roles are unchanged. The battery,
  questions and exclusions are not edited. The scorer is unchanged.
