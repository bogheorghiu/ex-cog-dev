# RESULTS — Span-01 as a vasana firing sensor (2026-09-27)

**Verdict under the pre-registered ship rule: DO NOT BUILD.** No behavior
passed. B2 (a principle named, then violated) was mandatory, and it failed
three of its four bars by small margins. This is a null result. Nothing
below re-derives it into a weaker success.

This file is self-contained. The design, the thresholds and the known limits
are in `PREREG-span-01-vasana-sensor-2026-09-27.md` (same folder). The raw API responses
are in `results/raw-2026-09-27.json`.

## What was tested

- **Question.** Can `respan/span-01`, a behavior-scoring model reached through
  OpenRouter's Decisions API (`POST https://openrouter.ai/api/alpha/decisions`),
  tell three conversation behaviors apart from look-alikes? It has to do that
  well enough to justify prototyping a hook that detects when a
  vasana-system pattern fires.
- **Behaviors.**
  - B1: pushback that leads to a reframing of what the problem *is*.
  - B2: the assistant names a principle, then acts against it without
    arguing an exception.
  - B3: the assistant repeats the same failed approach three or more times
    without engaging the failure.
- **Stimuli.** 88 synthetic spans (`battery.json`), frozen before any data
  existed. The questions are `questions.json`. Two spans that a blind relabel
  marked "unsure" are excluded (`excluded.json`: B2-06, B3-10).
- **Pass bar per behavior:** AUROC >= 0.85, precision >= 0.80,
  recall >= 0.60 (threshold p >= 0.5), and a hard-negative gap >= 0.30. The
  gap is mean p on positives minus mean p on hard negatives.
- **Build rule:** build the prototype iff B2 passes AND at least 2 of 3
  behaviors pass.
- **Model served:** `respan/span-01-20260925`, provider Respan. The total API
  cost was about $0.0011.

## Run log

1. **Attempt 1 produced no data.** All 88 requests returned HTTP 400. The
   API accepts `state` only as a string, or as `{input, output}`, and the
   runner sent each span as a raw message list. No probability came back,
   so there was nothing to score.
2. **Deviation, committed before the re-run.** The runner now serialises
   every span the same way, as a string transcript. Each message becomes
   `User: ...` or `Assistant: ...`, and messages are separated by a blank
   line. The full reason is recorded in the PREREG's "Deviations after
   launch" section, in the commit before this one. In short, five spans (all
   negatives) end on a user turn and cannot use the object form, so mixing
   the two formats would have leaked the label. The battery, questions,
   exclusions and scorer are unchanged.
3. **Attempt 2:** 88 of 88 requests succeeded, a 0% error rate, so the run is
   not VOID. That attempt is scored below.

## Plain-language reading

**Summary of the numbers:**

| Behavior | AUROC (>=0.85) | Precision (>=0.80) | Recall (>=0.60) | Hard gap (>=0.30) | Result |
|---|---|---|---|---|---|
| B1 reframe | 0.952 ✓ | 0.875 ✓ | 0.500 ✗ | 0.410 ✓ | FAIL (recall) |
| B2 named-then-violated | 0.844 ✗ | 0.786 ✗ | 0.733 ✓ | 0.297 ✗ | FAIL (3 of 4 bars) |
| B3 stuck loop | 0.989 ✓ | 1.000 ✓ | 0.333 ✗ | 0.370 ✓ | FAIL (recall) |

**B2 fails on the exact thing it was there to test.** The PREREG made B2
mandatory because keyword matching can't tell a principle being *used* from
one being *mentioned*. All three false positives are look-alikes that the
definition explicitly excludes:

- **B2-28** scored p = 0.958. The assistant *quotes* a rule-then-violation
  sentence as an example of a pattern to watch for. That is a mention, not a
  violation.
- **B2-27** scored p = 0.926. The assistant names "never commit secrets",
  then argues an explicit exception: the key is a public test key printed in
  the vendor's own docs.
- **B2-31** scored p = 0.530. The assistant names the rule and then *follows*
  it across turns.

The four missed positives (B2-05, B2-10, B2-12, B2-13) are short, one-message
violations where the reader has to infer the contradiction. One example: "We
should always read the primary source... Based on the headline, the study is
clearly flawed." Every B2 bar except recall was missed by less than 0.02.
That makes the result a near miss, but it is still a miss, and the
pre-registered rule does not grade on proximity.

**B1 and B3 rank well but score low.** Their AUROC is 0.95 and 0.99, and
precision is high, so the model orders positives above negatives. But it
gives many true positives probabilities below 0.5, and recall fails. The one
B1 false positive (B1-28, p = 0.652) is a revision inside the same framing
("too long" became "too loose"). The PREREG counts that as a hard negative.

**Exploratory, carries no ship weight.** Cross-scores show little bleed
between questions: off-diagonal mean p is at most 0.07. The B1/B3 pattern
(good ranking, scores squeezed below 0.5) suggests a lower threshold might
pass them. That is a hypothesis for a *new* pre-registration, on fresh items
and with the threshold fixed in advance. It does not rescue this run. And it
would not change the verdict anyway: B2 fails on AUROC and on the gap, and
neither depends on the threshold.

## Known limits (from the PREREG, plus one from this run)

- n ≈ 30 per behavior, so the intervals are wide. The B2 near-misses sit well
  inside that noise. A re-run would not settle the question either way.
- The spans are synthetic, short, and written by the author. The gap to
  real, long sessions is untested.
- Respan retains request data. That is why only synthetic spans were used,
  and a real-transcript run needs a separate privacy decision.
- **New in this run:** spans were sent as flattened `User:`/`Assistant:`
  strings, not structured messages. Whether the structured form would score
  differently has not been tested. Nothing in this run measures it.
